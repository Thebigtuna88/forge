## FRG-2 — Hook runtime, config files, settings.json, conformance framework

### In plain words

A *hook* is a small script that Claude Code runs before each of my commands. It can say "no"
(block), and Claude Code then refuses to run the command. FRG-2 builds the shared toolkit every
hook uses, the config files the hooks read, and a checker (`conformance`) that proves the hooks
block what they should. **FRG-2 has no gates of its own yet.** The first real gates (no push to
`main`, secret scan, …) come in FRG-3, so you won't need to restart Claude Code after FRG-2.
The first restart is after FRG-3 merges.

### What it delivers

| File | What it is |
|---|---|
| `.harness/lib/hookrt.sh` | the shared hook toolkit (below) |
| `.harness/mode.json` | per-hook `enforce` / `observe`; starts as `{"modes": {}}`, meaning everything enforces |
| `.harness/self-modification-paths.json` | the owner-only path list (spec 2.2), plus the two additions below |
| `.harness/deploy-targets.json` | deploy tools, and which of their commands count as production vs preview |
| `.claude/settings.json` | hook registration; empty (`{"hooks": {}}`) until FRG-3 adds the first gate |
| `.harness/bin/conformance` | the checker (spec 5.5) |
| `tests/unit/hookrt.test.sh`, `tests/unit/conformance.test.sh` | tests, written first and shown failing |
| `tests/fixtures/hooks/` | a sample hook used only by the tests, so the toolkit and checker can be proved before real hooks exist |

### `hookrt.sh`, the toolkit (spec 5.2, plus what Phase 1 taught)

- **Loading:** found next to the hook's own file, never via an environment variable. A hook
  whose toolkit fails to load blocks (exit 2).
- **Fail closed by construction (new).** A hook allows a command only by calling `hr_allow`.
  If a hook crashes, hits a typo, or simply reaches its end without deciding, the toolkit turns
  that into a block. (In Claude Code any exit code other than 2 means "allow", so a hook that
  crashes would otherwise let the command through.)
- **`hr_init <hook>`:** reads Claude Code's JSON (tool, command, file path, folder). Reads
  the hook's mode from `mode.json`. Missing file, broken JSON, unknown value or missing entry all
  mean `enforce`. If `jq` or `python3` is missing, it blocks. Unreadable input also blocks. A
  hook with two parts can have a separate mode for each, e.g. `guard-live-checkout:bash`.
- **`hr_deny "<reason>"`:** enforce mode blocks and shows me the reason. Observe mode writes
  `<utc> <hook> WOULD-DENY <reason> :: <command>` to `.harness/observed.log` and allows.
- **`hr_tokens`:** splits a command into words with Python's `shlex`, which handles quotes the
  way the shell does. If the quoting doesn't parse, any guarded command is blocked.
- **`hr_require_simple`:** if a command mentions a guarded action (`git push`, `git commit`,
  `gh pr merge`, `gh api`, `gh repo`, `gh workflow run`, or any deploy tool), it must be one
  plain command. It must start with the tool itself. It may not contain `&&` `||` `;` `|` `&`
  `>` `<`, newlines, backticks or `$`. Glob and brace characters are refused too, because the
  shell would expand them into something the hook never saw. Words are found after removing
  quotes and backslashes, so `g"i"t p\ush` still counts as `git push`. **Accepted side effect:**
  a chained command that only *mentions* those words, like `git log | grep commit`, is also
  blocked and has to be run as separate commands.
- **`hr_git_sub`:** finds git's subcommand after global options (`-C <dir>`, `-c k=v`,
  `--no-pager`, …). It reports "unknown" for an option it doesn't recognise, and guards treat
  unknown as a block. A git **alias** that runs a shell (`!…`) or expands to a guarded
  subcommand is blocked. So is `-c alias.*=…` on the command line.
- **`hr_md5`, `hr_sha256`:** checksum helpers that work the same on macOS and in CI.
- macOS `/bin/bash` 3.2 only. The hooks never rely on my shell's functions (Phase 1 found that
  `grep` is a broken shell function inside my Bash tool; hooks run as their own process, so
  they're unaffected).

### Conformance (spec 5.5)

1. Every hook in `.claude/hooks/` is executable, registered, and passes shellcheck. Every
   registered hook exists.
2. **Sandbox (new detail).** Conformance copies the hooks, toolkit and config into a temporary
   folder laid out like the real thing: a "main checkout" on `dev`, a worktree folder next to it,
   and a local stand-in for GitHub. It checks the copies are byte-identical to the live files,
   including the live `mode.json`. It then feeds each fixture
   (`tests/conformance/<hook>/{deny,allow}/<case>.json`) to the hook there. Fixtures can use the
   placeholders `@ROOT@`, `@WORKTREES@` and `@TMP@`. An optional `<case>.setup.sh` prepares
   things like a git alias. This lets FRG-3's "no commit on the main checkout" cases run for
   real without touching `~/code/forge`.
   - enforce: deny cases exit 2, allow cases exit 0;
   - observe: deny cases exit 0 **and** add a `WOULD-DENY` line.
3. In the sandbox, a missing, broken and unknown-value `mode.json` each make every hook's deny
   cases block.
4. Hooks are not switched off: no `disableAllHooks` in `~/.claude/settings.json`,
   `~/.claude/settings.local.json`, `.claude/settings.json` or `.claude/settings.local.json`.
5. Prints `hook | mode | deny cases | allow cases | result` and exits non-zero on any failure.
   With no hooks yet, it still runs checks 3–4 and says "0 hooks".

### Owner-only list: two additions (recommended)

Besides the spec 2.2 list, I recommend adding **`.harness/bin/conformance`** and
**`tests/conformance/`**. Weakening the checker, or deleting a "must block" test case, would
make a broken gate look healthy. I'm allowed to merge any reviewed PR that touches no owner-only
path (spec 12), so without these additions such a change could reach `dev` without you.

### `deploy-targets.json` shape

`{"tools": [...], "production": [[words…], …], "preview": [[words…], …]}`. An entry matches when
the command starts with the entry's first word and contains each of its other words. Example:
`["vercel", "--prod"]` catches `vercel --prod` and `vercel deploy --prod`. It is filled with the
spec 5.3 production list and `vercel deploy` as preview. FRG-5 builds the gate that reads it.
(Built: a plain `["vercel"]` preview entry was left out. Under the "contains" rule it would match
every vercel command, including `vercel env rm`, so plain `vercel` is denied and
`vercel deploy` is used instead. A word also matches itself followed by `=value`, so
`--prod=true` counts as `--prod`.)

### Tests that must fail first, then pass

- `hookrt`: each of the four bad `mode.json` cases means enforce. Observe logs and allows.
  Missing or failed toolkit blocks. A crash or no decision blocks. Missing `jq` blocks. Broken
  input blocks. Quoting tricks, `-C`, aliases and chained commands are each handled by
  `hr_require_simple` / `hr_git_sub`.
- `conformance`: passes on a good sample. Fails, one test each, on: an unregistered hook, a
  registered hook that's missing, a non-executable hook, a shellcheck failure, a deny case that
  allows, an allow case that blocks, observe without a `WOULD-DENY` line, a copy that differs
  from the live file, and `disableAllHooks` set.
- `bash tests/run.sh` → `ALL PASS`, conformance stage included.

### Changes from review (round 1)

- The hook header gains one line, `unset HOOKRT_LOADED`, before `source`. An inherited
  `HOOKRT_LOADED=1` can't make an empty runtime look loaded.
- hookrt runs with errexit. Only `hr_allow` allows. Every catchable terminating signal, a
  failed command and a missing decision all deny. Its private state is reset when it loads.
- `hr_part <part>` lets one hook give a part its own mode (`guard-live-checkout:bash`).
- `mode.json` counts only if it is one JSON object whose entry is exactly `"observe"`.
- `~` is refused in guarded commands. Quoting is lost after parsing, so the hook can't tell
  whether the shell would expand it. Line continuations are removed before matching. A command
  name built by the shell (`$…`, `{…}`) or a glob that could become git, gh or a deploy tool
  (`/usr/bin/g[i]t`) counts as guarded.
- Conformance also checks that each case's event and tool are covered by a synchronous
  registration. Setup scripts and hooks run with `env -i` and a sandbox HOME. Placeholders are
  filled by jq, not sed. Bad-mode runs check the sandbox copies too, and observe needs a *new*
  line under the case's own key. Symlinks and stray or hidden files are refused, and live files
  must not change while it runs. Its hooks-off check covers `$CLAUDE_CONFIG_DIR`, the main
  checkout's settings when run from a worktree, macOS managed settings, and
  `allowManagedHooksOnly`.

### Changes from review (round 2)

- Every hook starts with `#!/bin/bash -p`. Privileged mode makes bash ignore exported functions,
  `BASH_ENV`, `SHELLOPTS` and `CDPATH`, so the environment can't replace `jq`, `git` or the
  runtime's own functions. The runtime refuses to run without it, and conformance checks the
  first line.
- The hook input must be exactly one JSON object. After a wrapper (`env`, `nice`, `xargs`, …,
  also by absolute path), every word up to the next operator is checked as a possible command
  name. A file-descriptor number before a redirection (`2>f`) doesn't end the command position.
- Conformance: setup scripts run under macOS `sandbox-exec` and may write only inside their
  sandbox. The live-change check covers the whole checkout (outside `.git`, `work/`, `projects/`,
  `.harness/state/`). Symlinks are refused in the hook, runtime and config paths. A `*ToolUse`
  case must name its tool. A registration with no matcher covers every tool.

### Changes from review (round 3)

- The runtime sets PATH itself, with system folders first (`/usr/bin:/bin:/usr/sbin:/sbin`,
  then Homebrew). So jq, python3, git, shasum and md5 come from root-owned folders. Tests that
  need stub tools (FRG-4's `gh`) edit the PATH line in their own copy of the runtime. `gh` and
  `gitleaks` still come from Homebrew, which the user account can write to. That limit belongs
  with spec 11 L1 and is recorded there when FRG-4 adds those gates.
- errtrace plus an ERR trap: a failure inside `$(…)` also denies, so hooks write
  `x="$(cmd || true)"` where a failure is expected. `exec` is refused. A raw NUL byte in the
  input makes it invalid instead of vanishing.
- `<(…)` and `>(…)` open a command position.
- Conformance runs a case's setup before the bad-mode variant goes in. A setup may not change
  any copied file, and the variant must still be in place after the hook has run.

### Changes from review (round 4)

- The `exec` builtin is switched off in hooks (`enable -n exec`). `GIT_*` and `DEVELOPER_DIR`
  are cleared, so the hook sees git's own defaults. A command containing `$'…'` or `$"…"`
  counts as guarded. The checksum helpers read the file on stdin.
- Conformance itself runs as `#!/bin/bash -p` with its own PATH. A case must be valid hook
  input. The runner's files live outside what a setup may write, and a setup may not put
  symlinks in the sandbox's hook, runtime or config paths.

### Changes from review (round 5)

- Hooks and conformance clear the environment down to an allowlist (HOME, USER, LOGNAME, TMPDIR,
  plus CLAUDE_PROJECT_DIR for hooks or CLAUDE_CONFIG_DIR for conformance). This removes
  PERL5OPT, which `shasum` (a Perl script) would obey, along with GIT_* and the rest.
- A failed command inside any `$(…)` leaves a "failed" mark in the hook's private temp folder,
  and the exit check reads it. So `local x="$(cmd)"` and `"$(cmd)"` as an argument also deny.
- A glob with a letter in its last part that could match git, gh or a deploy tool counts as
  guarded wherever it stands, and so does any brace expansion. That covers wrappers the runtime
  doesn't know. `arch`, `xcrun` and similar are added to the wrapper list.
- A setup runs under a sandbox that refuses writes to the copied hooks, runtime and config (and
  to the folders holding them) and refuses all signals. That also binds anything the setup
  leaves running. A case's NUL check covers every field. Setup scripts are trusted, reviewed,
  owner-only code: they shape the scene a case runs in.

### Changes from review (round 6)

- A deny case counts only if the hook really decided. It must print the runtime's
  `BLOCKED by FORGE hook <key>:` line, or in observe mode log `WOULD-DENY`. A crash prints a
  different message. A case may name its expected reason in `forge_reason`.
- A hook may use `$(…)` only as the whole value of a plain assignment, and no backticks or
  `<( >(` (conformance checks its source). Then a deny, an unset variable or a signal inside the
  substitution fails the assignment and denies. `hr_deny` also leaves the "failed" mark.
- `HR_WORKTREES` is right when the runtime loads from a ticket worktree.

### Changes from review (round 7)

- The source check allows at most one `$(…)` per line, as the whole value of one plain
  assignment, and no nesting. The standard header line is the only exception.

### Changes from review (round 8)

- A hook defines no functions and opens no multi-line `{ }` or `( )` groups. Bash stops checking
  for errors inside those when they are used as a condition, which would hide a failed `$(…)`.
  Conformance checks this along with the other source rules.
- Conformance rejects control characters in registration fields. It reads an observe case's
  `forge_reason` only from the reason field of the line that run added.

### Changes from review (round 9)

- The source check reads hooks as real shell words with Python's shlex, which understands
  quoting and comments. It tracks every `{ }` and `( )` group, and a group must close on the line
  it opens. `if { # comment` can no longer hide one.

### Changes from review (round 10)

- The source check tracks conditions across lines: from `if`, `elif`, `while` or `until` up to
  `then` or `do`, and lines continued by `&&`, `||`, `|` or `\`. A `$(…)` may not appear in
  them. Words keep their quotes, so a quoted `(` or `{` is just a character.

### Changes from review (round 11)

- The source check reads quoting with a small scanner of its own instead of non-POSIX shlex.
  The scanner blanks out quoted parts, escapes and comments the way the shell reads them, so
  permitted lines such as `m="$(hr_md5 "$HR_FILE")"` pass. A test now covers the permitted forms.

### Changes from review (round 12)

- The source check recognises reserved words only where a command starts, and keeps nested
  `if`/`while`/`until`/`for`/`case` blocks on a stack. An argument named `then` can't end a
  condition, and a nested `fi` can't end the outer one. If the block structure stops adding up,
  everything after it counts as a condition (fail closed).

### Changes from review (round 13)

- The source check first joins `\` continuations into the logical lines the shell sees. Each
  `if`/loop/`case` block remembers the `$(…)` lines inside it, nested blocks included. If the
  block is itself tested (`&&`, `||`, `!` or `|` before it, or `&&`, `||` or `|` after its
  closing word), those lines are refused, because bash ignores errors in the whole block.

### Changes from review (round 14)

- The source check looks past redirections after a closing `fi`/`done`/`esac` for `&&`, `||` or
  `|`, and treats `time`'s options as still coming before the command.
- In the runtime, `find` is a known wrapper (`-exec` runs a command). A glob without letters
  (`/tmp/bin/???`) counts as guarded when the command also names a guarded verb.

### Changes from review (round 15)

- The source check joins a line only where the shell would: a backslash ending a comment
  doesn't join. It checks the assignment rule on the line without its comment. A hook may not
  use a here-document (`<<`), whose text would otherwise be read as code. `<<<` is still allowed.

### Changes from review (round 16)

- The runtime sets `pipefail`, so a failure in any part of a pipeline counts. The inside of a
  permitted `$(…)` must be a simple command or a pipeline (no `;`, `&&`, `||`, `&`, groups, `!`
  or compound commands).
- An allow case may not add a `WOULD-DENY` line under any key.

### Changes from review (round 17)

- The runtime's word scan also splits on hyphens, so git's own `git-push` and `git-commit`
  programs read as `git push` and `git commit`. `git send-pack` and `git http-push` (which also
  push) are guarded. `git -c` is accepted only for display settings (`color.*`,
  `core.quotepath`, `advice.*`), because many other settings run programs.
- The source check no longer skips `$((`, so any `$((…))` in a hook is refused, since bash may
  read it as a command substitution. The observe reason reaches awk through the environment, so
  backslashes stay literal. The runtime's guidance on expected failures matches the rules.

### Changes from review (round 18)

- A hook may not use `eval`, `source` or `.` (the header's `source` of the runtime is the one
  exception). Inside a `$(…)`, shells and command wrappers (`sh`, `env`, `xargs`, …) are refused
  too. The runtime refuses aliases for every guarded git command.
- In conformance the hook itself runs under the sandbox. It, and any program git starts for it,
  may write only inside its sandbox folder and may not send signals. The live-change check is
  now tested by changing a live file while conformance runs.

### Changes from review (round 19)

- A command name in a hook must be a plain word, with no quotes, escapes, `$` or globs, so the
  source check reads it as bash does. Command position carries through assignment and
  redirection prefixes. At the top level a hook may not run `eval`, `source`, `.`, `command`,
  `builtin`, `exec`, `env`, `trap`, `set`, `shopt`, `enable`, `unset` or a shell (the header's
  `unset` and `source` lines are exempt). Inside `$(…)`, wrappers like `arch`, `xargs` and `nice`
  are refused too. `case` patterns and `[[ … ]]` tests are not read as commands.

### Changes from review (round 20)

- The source check recognises a redirection wherever it stands, so the file name after it
  (`printf x > "$HR_ROOT/out"`) is not read as a command name.

### Changes from review (round 21)

- After `gh`, any word the shell would expand (glob, `$`, braces, backticks) makes the command
  guarded, because it could become gh's subcommand (`gh pr m???e` → `gh pr merge`). git's
  subcommand was already checked exactly, and a deploy tool already made a command guarded.

### Review and merge

Hand-run codex `code` and `security` lenses, as in FRG-1, until both are CLEAN. Then an
owner-merge handoff, because every file here except the tests is owner-only.

## FRG-3 — Git gates: push, secret scan, branch names, shared checkout, history rewrite

### In plain words

These are the first real gates. Once FRG-3 is merged and you restart Claude Code, five hooks
check every command I run that touches git. They block:

1. **a push to `main` or `dev`**, or any forced or deleting push;
2. **a commit with a secret in it**, and any way of committing other than the one approved form;
3. **a badly named branch**;
4. **a commit in the main folder** (`~/code/forge`, or a project's main folder) instead of a
   ticket's worktree;
5. **rewriting history** (rebase, amend and the like).

GitHub's branch protection stays as a second, independent layer behind the first.

### What it delivers

| File | What it is |
|---|---|
| `.claude/hooks/deny-push-to-protected.sh` | gate 1 |
| `.claude/hooks/secret-scan.sh` | gate 2 |
| `.claude/hooks/enforce-branch-format.sh` | gate 3 |
| `.claude/hooks/deny-commit-on-shared-checkout.sh` | gate 4 |
| `.claude/hooks/deny-history-rewrite.sh` | gate 5 |
| `.claude/settings.json` | registers all five for `PreToolUse` / `Bash` |
| `.harness/gitleaks.toml` | the secret-scan rules: gitleaks' defaults, owned by FORGE |
| `tests/conformance/<hook>/{deny,allow}/` | must-block and must-allow cases for each gate |
| `.harness/lib/hookrt.sh` | small additions: more guarded git commands (below) |
| `.harness/self-modification-paths.json` | adds `.harness/gitleaks.toml` (recommended, below) |

Every gate is built on the FRG-2 runtime and must pass conformance. Both pin how gates are
written: `#!/bin/bash -p`, decisions only through `hr_deny` / `hr_allow`, plain command names,
and the other source rules.

### What each gate allows (everything else is blocked)

1. **deny-push-to-protected.** A push is allowed in exactly one form:
   `git push [-u | --set-upstream] origin <branch>`, where `<branch>` is a ticket branch
   (`feature/<KEY>-<n>-<slug>`). That rules out pushing to `main` or `dev` in any spelling
   (`HEAD:main`, `refs/heads/dev`, `:main`), `--force`, `-f`, `--force-with-lease`, `+refspec`,
   `--delete`, `--mirror`, `--all`, `--prune`, `--tags`, other remotes and a bare `git push`.
   `git send-pack` and `git http-push` are blocked outright.
2. **secret-scan.** A commit is allowed only as `git commit -F <file>` (or `--file=<file>`),
   with no `-m`, `-a`, `--amend`, `--no-verify` or other options, and only if
   `gitleaks git --staged` finds nothing. gitleaks runs with FORGE's own rules
   (`--config .harness/gitleaks.toml`), ignores any `.gitleaksignore` and `gitleaks:allow`
   comments in the repository, and **a missing gitleaks blocks the commit**. Other ways of making
   a commit skip the scan, so they are blocked: `git commit-tree`, `git am`, `git cherry-pick`,
   `git revert`. (`git merge dev` stays allowed, as the charter's way to update a branch. It only
   brings in commits that were already scanned.)
3. **enforce-branch-format.** Creating or renaming a branch (`git checkout -b/-B`,
   `git switch -c/-C`, `git branch <name>` / `-m`, `git worktree add -b/-B`), and pushing one,
   needs a name matching `^feature/[A-Z]{3}-[0-9]+-[a-z0-9]+(-[a-z0-9]+)*$` with a known key.
   For now the only known key is `FRG`; projects' keys arrive with `projects.json` in FRG-10.
4. **deny-commit-on-shared-checkout.** A commit runs in a folder known for certain: the
   command's folder, or its `git -C`. That folder's repository must be a worktree under
   `~/code/forge-worktrees/`, on a `feature/…` branch. A commit in `~/code/forge` or
   `~/code/forge/projects/<name>` is blocked, and so is one whose folder or branch can't be
   determined.
5. **deny-history-rewrite.** Blocks `git rebase`, `git commit --amend`, `git filter-branch`,
   `git filter-repo`, `git replace`, any `git update-ref` and `git branch -f`. A forced push is
   already blocked by gate 1.

**Runtime additions (needed so a chained command can't hide these).** These git commands join
the guarded list, so each must be one plain command: `rebase`, `filter-branch`, `filter-repo`,
`replace`, `update-ref`, `commit-tree`, `am`, `cherry-pick`, `revert`, `checkout`, `switch`,
`branch` and `worktree`. An alias for any of them is refused, as it already is for push and
commit. The cost: something like `git branch --show-current | cat` has to be split into
separate commands.

### Owner-only list: one addition (recommended)

Add **`.harness/gitleaks.toml`**. Loosening its rules would let secrets through the scan just
as surely as weakening the gate, so it should change only by a PR you merge.

### Tests and proof

- A conformance case for each blocked and each allowed form above, run in the sandbox.
  Setup scripts create the main checkout's first commit, a ticket worktree, a staged fake
  secret (built at run time from pieces, so no secret-looking text sits in the repository) and
  aliases. Quoting tricks, `-C`, aliases and chained forms are covered per spec 10.3.
- `bash tests/run.sh` → `ALL PASS`.
- **Live proof (Phase 2 exit).** After you merge and restart, I try one blocked command per gate
  in this session and save the transcript under `work/`. Each attempt is harmless even if a gate
  failed: a push to `main` is also refused by GitHub, and the commit, rebase and branch attempts
  run in a throwaway worktree.

### Changes from review (round 1)

- checkout, switch, branch and worktree add accept only the options the branch-name gate lists,
  spelled in full. Abbreviations (`--creat`) and clusters (`-qm`) are refused. Implicit creation
  is checked too: `--track <remote>/<name>`, a name git creates from a remote branch, and
  `worktree add <path>` naming the branch after its folder. `-v` no longer turns the check off.
  `--` ends option parsing.
- The history gate also refuses `git reset` except unstaging (`git reset [-q] [HEAD] [-- <paths>]`),
  `checkout -B`, `switch -C`/`--force-create` and `worktree add -B` (they reset a branch), fetch
  with `--force`/`-u` or a refspec with `:` or `+`, `pull --rebase`, and abbreviated or clustered
  force options.
- Merge and pull: in a ticket worktree, merge only as `git merge [--no-edit] [--no-ff|--ff-only]
  [--squash] <branch>` or `--abort`. A conflicted merge is concluded with `git commit -F`, which
  is scanned. Pull only with `--ff-only`. In a main checkout, merge and pull only `--ff-only`.
  The charter now says to update the main checkout with `git pull --ff-only origin dev`.
- The secret scan reads the staged files' raw blobs from git's index (so `.gitattributes` can't
  hide them), refuses a linked message file and a staged submodule, and a commit must be in a
  linked worktree, not a standalone repository placed under forge-worktrees.
- `reset`, `merge`, `pull` and `fetch` join the runtime's guarded git commands.

### Changes from review (round 2)

- After `--`, branch, switch and worktree add still read branch names (only checkout reads paths).
  Fetch accepts only `-q` and `--prune`, plus plain branch names after the repository.
  `git fast-import` is refused, and `git symbolic-ref` may only read; both are guarded.
- The secret scan keeps the staged files' own paths (gitleaks matches some secrets by file name),
  lists the whole index whatever folder it runs from (`--no-relative`), and uses an empty ignore
  folder of its own.
- In a main checkout, merge and pull may use `--ff-only` and no other option. In a worktree,
  merge and pull get the same linked-worktree and feature-branch checks as commit.

### Changes from review (round 3)

- Git commands are now on an allowlist. The runtime knows which git commands are read-only or
  harmless (status, log, diff, add, remote, tag, …); every other one is guarded. The history gate
  refuses any guarded git command that no gate checks: `git history`, `git replay`, and anything
  a newer git adds. `git stash` is limited to push/save/pop/apply/drop/clear/list/show.
- Fetch and pull are refused while a configured `remote.*.fetch` mapping writes outside
  `refs/remotes/`. Pull refspecs with `:` or `+` are refused, and after `--` fetch and pull
  operands are still checked.
- `git worktree add <path>/` names its branch after the folder even with a trailing slash.

### Changes from review (round 4)

- `remote` and `tag` leave the runtime's safe list. `git remote update` and `remote add -f`
  are refused (use `git fetch`, whose mappings are checked). A tag may be listed or made plain,
  but a tag with a message (`-a`, `-s`, `-u`, `-m`, `-F`, `-e`) is refused: its text would go
  into git unscanned, and `push.followTags` could carry it along with a branch.
- `git submodule` is limited to status, summary, init, sync, absorbgitdirs, deinit and update
  without `--merge`/`--rebase` (no `foreach`). Notes may only be read.
- `git branch -m` / `-c` checks the new name even when a listing option is given with it.

### Changes from review (round 5)

- Every command the history gate allows conditionally now has an allowlist of exact options, so
  attached or abbreviated forms (`-mTEXT`, `--mes=`, `--fet`) are refused. tag: listing, deleting
  and verifying only, and a plain tag is refused while `tag.gpgSign` is set (unless `--no-sign`).
  remote add: `-t`, `-m`, `--tags`, `--no-tags`. submodule update: listed options, and
  `--checkout` must be said, overriding a configured merge or rebase. reflog: read only.
- `init` and `clone` leave the safe list: a new repository or clone may start only on `dev` or
  `main`. `git branch --sort=… <name>` creates a branch, so its name is checked.

### Changes from review (round 6)

- Git configuration can change what an allowed command does, so the gates now check it first:
  - push is refused while `remote.origin.push` or `remote.origin.mirror` is set, or while
    old-style `.git/remotes` / `.git/branches` files exist (fetch and pull too);
  - fetch mappings must have the standard shape, `refs/heads/<x>:refs/remotes/<name>/<x>`;
  - merge is refused while `branch.*.mergeOptions` is set, and pull while `pull.rebase` or
    `branch.*.rebase` is;
  - `init` and `clone` must name `-b dev` or `-b main`, because otherwise configuration or the
    remote picks the branch (FRG-10's scaffolder will pass `-b dev`);
  - `--track` and branches git would guess from a remote must be named explicitly with -b / -c.
- The secret scan runs twice, under real file names and under neutral names, because gitleaks'
  default rules skip some paths (package-lock.json, node_modules, …) entirely. The message is
  scanned under a neutral name. The staged list ignores submodule-hiding settings.

### Changes from review (round 7)

- A command that names a `.git` path (`.git/refs/…`, `…/.git`) is guarded and refused by the
  runtime. Writing git's own files moves branches without any git command (`git log --output=`,
  `echo … > .git/refs/heads/dev`). git's own programs (`git-tag`, `git-remote`, …) in command
  position are guarded too, so they must be called as `git <name>`.
- Merge is refused while `merge.branchdesc` or a branch description is set (the message would be
  unscanned). `init --template` is refused, and init/clone are refused while `init.templateDir`
  is set. The tag-signing check applies only when a tag is created.

### Changes from review (round 8)

- Saving a stash (`git stash`, `stash push`, `stash save`, `stash -u`) is refused: a stash is a
  commit made without the secret scan. Restoring, listing and dropping stashes stays allowed.
- `git remote` refuses any option before the subcommand except `-v`/`--verbose`, and refuses
  `remote prune` (use `git fetch --prune`, which gets the mapping checks).
- `git submodule update` stops reading options at `--`, so a path can't stand in for
  `--checkout`.
- `git init --separate-git-dir` is refused: reinitializing would move git's files out of `.git`,
  past the runtime's `.git` path guard. `init.templateDir` is read from the folder the command
  runs in (`git -C <dir>`).

### What changes for me after the restart

Some commands I use today will be blocked, by design. The main one: a search for text like
`git push` (`grep "git push" file`) mentions a guarded action without being that action (spec
5.2's accepted side effect). I'll use the Read tool for that instead. The same goes for
looking at git's own files (`cat .git/config`): I'll use git commands (`git config --list`).

because hooks, settings and runtime are owner-only. Then you restart Claude Code.
