## FRG-2 — Hook runtime, config files, settings.json, conformance framework

### In plain words

A *hook* is a small script that Claude Code runs before each of my commands. It can say "no"
(block), and Claude Code then refuses to run the command. FRG-2 builds the shared toolkit every
hook uses, the config files the hooks read, and a checker (`conformance`) that proves the hooks
block what they should. **FRG-2 has no gates of its own yet.** The first real gates (no push to
`main`, secret scan, …) come in FRG-3, so you won't need to restart Claude Code after FRG-2.
The first restart is after FRG-3 merges.

### What it delivers

| File | What it is |
|---|---|
| `.harness/lib/hookrt.sh` | the shared hook toolkit (below) |
| `.harness/mode.json` | per-hook `enforce` / `observe`; starts as `{"modes": {}}`, meaning everything enforces |
| `.harness/self-modification-paths.json` | the owner-only path list (spec 2.2), plus the two additions below |
| `.harness/deploy-targets.json` | deploy tools, and which of their commands count as production vs preview |
| `.claude/settings.json` | hook registration; empty (`{"hooks": {}}`) until FRG-3 adds the first gate |
| `.harness/bin/conformance` | the checker (spec 5.5) |
| `tests/unit/hookrt.test.sh`, `tests/unit/conformance.test.sh` | tests, written first and shown failing |
| `tests/fixtures/hooks/` | a sample hook used only by the tests, so the toolkit and checker can be proved before real hooks exist |

### `hookrt.sh`, the toolkit (spec 5.2, plus what Phase 1 taught)

- **Loading:** found next to the hook's own file, never via an environment variable. A hook
  whose toolkit fails to load blocks (exit 2).
- **Fail closed by construction (new).** A hook allows a command only by calling `hr_allow`.
  If a hook crashes, hits a typo, or simply reaches its end without deciding, the toolkit turns
  that into a block. (In Claude Code any exit code other than 2 means "allow", so a hook that
  crashes would otherwise let the command through.)
- **`hr_init <hook>`:** reads Claude Code's JSON (tool, command, file path, folder). Reads
  the hook's mode from `mode.json`. Missing file, broken JSON, unknown value or missing entry all
  mean `enforce`. If `jq` or `python3` is missing, it blocks. Unreadable input also blocks. A
  hook with two parts can have a separate mode for each, e.g. `guard-live-checkout:bash`.
- **`hr_deny "<reason>"`:** enforce mode blocks and shows me the reason. Observe mode writes
  `<utc> <hook> WOULD-DENY <reason> :: <command>` to `.harness/observed.log` and allows.
- **`hr_tokens`:** splits a command into words with Python's `shlex`, which handles quotes the
  way the shell does. If the quoting doesn't parse, any guarded command is blocked.
- **`hr_require_simple`:** if a command mentions a guarded action (`git push`, `git commit`,
  `gh pr merge`, `gh api`, `gh repo`, `gh workflow run`, or any deploy tool), it must be one
  plain command. It must start with the tool itself. It may not contain `&&` `||` `;` `|` `&`
  `>` `<`, newlines, backticks or `$`. Glob and brace characters are refused too, because the
  shell would expand them into something the hook never saw. Words are found after removing
  quotes and backslashes, so `g"i"t p\ush` still counts as `git push`. **Accepted side effect:**
  a chained command that only *mentions* those words, like `git log | grep commit`, is also
  blocked and has to be run as separate commands.
- **`hr_git_sub`:** finds git's subcommand after global options (`-C <dir>`, `-c k=v`,
  `--no-pager`, …). It reports "unknown" for an option it doesn't recognise, and guards treat
  unknown as a block. A git **alias** that runs a shell (`!…`) or expands to a guarded
  subcommand is blocked. So is `-c alias.*=…` on the command line.
- **`hr_md5`, `hr_sha256`:** checksum helpers that work the same on macOS and in CI.
- macOS `/bin/bash` 3.2 only. The hooks never rely on my shell's functions (Phase 1 found that
  `grep` is a broken shell function inside my Bash tool; hooks run as their own process, so
  they're unaffected).

### Conformance (spec 5.5)

1. Every hook in `.claude/hooks/` is executable, registered, and passes shellcheck. Every
   registered hook exists.
2. **Sandbox (new detail).** Conformance copies the hooks, toolkit and config into a temporary
   folder laid out like the real thing: a "main checkout" on `dev`, a worktree folder next to it,
   and a local stand-in for GitHub. It checks the copies are byte-identical to the live files,
   including the live `mode.json`. It then feeds each fixture
   (`tests/conformance/<hook>/{deny,allow}/<case>.json`) to the hook there. Fixtures can use the
   placeholders `@ROOT@`, `@WORKTREES@` and `@TMP@`. An optional `<case>.setup.sh` prepares
   things like a git alias. This lets FRG-3's "no commit on the main checkout" cases run for
   real without touching `~/code/forge`.
   - enforce: deny cases exit 2, allow cases exit 0;
   - observe: deny cases exit 0 **and** add a `WOULD-DENY` line.
3. In the sandbox, a missing, broken and unknown-value `mode.json` each make every hook's deny
   cases block.
4. Hooks are not switched off: no `disableAllHooks` in `~/.claude/settings.json`,
   `~/.claude/settings.local.json`, `.claude/settings.json` or `.claude/settings.local.json`.
5. Prints `hook | mode | deny cases | allow cases | result` and exits non-zero on any failure.
   With no hooks yet, it still runs checks 3–4 and says "0 hooks".

### `deploy-targets.json` shape

`{"tools": [...], "production": [[words…], …], "preview": [[words…], …]}`. An entry matches when
the command starts with the entry's first word and contains each of its other words. Example:
`["vercel", "--prod"]` catches `vercel --prod` and `vercel deploy --prod`. It is filled with the
spec 5.3 production list and `vercel deploy` as preview. FRG-5 builds the gate that reads it.
(Built: a plain `["vercel"]` preview entry was left out. Under the "contains" rule it would match
every vercel command, including `vercel env rm`, so plain `vercel` is denied and
`vercel deploy` is used instead. A word also matches itself followed by `=value`, so
`--prod=true` counts as `--prod`.)

### Tests that must fail first, then pass

- `hookrt`: each of the four bad `mode.json` cases means enforce. Observe logs and allows.
  Missing or failed toolkit blocks. A crash or no decision blocks. Missing `jq` blocks. Broken
  input blocks. Quoting tricks, `-C`, aliases and chained commands are each handled by
  `hr_require_simple` / `hr_git_sub`.
- `conformance`: passes on a good sample. Fails, one test each, on: an unregistered hook, a
  registered hook that's missing, a non-executable hook, a shellcheck failure, a deny case that
  allows, an allow case that blocks, observe without a `WOULD-DENY` line, a copy that differs
  from the live file, and `disableAllHooks` set.
- `bash tests/run.sh` → `ALL PASS`, conformance stage included.

### Changes from review (round 1)

- The hook header gains one line, `unset HOOKRT_LOADED`, before `source`. An inherited
  `HOOKRT_LOADED=1` can't make an empty runtime look loaded.
- hookrt runs with errexit. Only `hr_allow` allows. Every catchable terminating signal, a
  failed command and a missing decision all deny. Its private state is reset when it loads.
- `hr_part <part>` lets one hook give a part its own mode (`guard-live-checkout:bash`).
- `mode.json` counts only if it is one JSON object whose entry is exactly `"observe"`.
- `~` is refused in guarded commands. Quoting is lost after parsing, so the hook can't tell
  whether the shell would expand it. Line continuations are removed before matching. A command
  name built by the shell (`$…`, `{…}`) or a glob that could become git, gh or a deploy tool
  (`/usr/bin/g[i]t`) counts as guarded.
- Conformance also checks that each case's event and tool are covered by a synchronous
  registration. Setup scripts and hooks run with `env -i` and a sandbox HOME. Placeholders are
  filled by jq, not sed. Bad-mode runs check the sandbox copies too, and observe needs a *new*
  line under the case's own key. Symlinks and stray or hidden files are refused, and live files
  must not change while it runs. Its hooks-off check covers `$CLAUDE_CONFIG_DIR`, the main
  checkout's settings when run from a worktree, macOS managed settings, and
  `allowManagedHooksOnly`.

### Changes from review (round 2)

- Every hook starts with `#!/bin/bash -p`. Privileged mode makes bash ignore exported functions,
  `BASH_ENV`, `SHELLOPTS` and `CDPATH`, so the environment can't replace `jq`, `git` or the
  runtime's own functions. The runtime refuses to run without it, and conformance checks the
  first line.
- The hook input must be exactly one JSON object. After a wrapper (`env`, `nice`, `xargs`, …,
  also by absolute path), every word up to the next operator is checked as a possible command
  name. A file-descriptor number before a redirection (`2>f`) doesn't end the command position.
- Conformance: setup scripts run under macOS `sandbox-exec` and may write only inside their
  sandbox. The live-change check covers the whole checkout (outside `.git`, `work/`, `projects/`,
  `.harness/state/`). Symlinks are refused in the hook, runtime and config paths. A `*ToolUse`
  case must name its tool. A registration with no matcher covers every tool.

### Changes from review (round 3)

- The runtime sets PATH itself, with system folders first (`/usr/bin:/bin:/usr/sbin:/sbin`,
  then Homebrew). So jq, python3, git, shasum and md5 come from root-owned folders. Tests that
  need stub tools (FRG-4's `gh`) edit the PATH line in their own copy of the runtime. `gh` and
  `gitleaks` still come from Homebrew, which the user account can write to. That limit belongs
  with spec 11 L1 and is recorded there when FRG-4 adds those gates.
- errtrace plus an ERR trap: a failure inside `$(…)` also denies, so hooks write
  `x="$(cmd || true)"` where a failure is expected. `exec` is refused. A raw NUL byte in the
  input makes it invalid instead of vanishing.
- `<(…)` and `>(…)` open a command position.
- Conformance runs a case's setup before the bad-mode variant goes in. A setup may not change
  any copied file, and the variant must still be in place after the hook has run.

### Changes from review (round 4)

- The `exec` builtin is switched off in hooks (`enable -n exec`). `GIT_*` and `DEVELOPER_DIR`
  are cleared, so the hook sees git's own defaults. A command containing `$'…'` or `$"…"`
  counts as guarded. The checksum helpers read the file on stdin.
- Conformance itself runs as `#!/bin/bash -p` with its own PATH. A case must be valid hook
  input. The runner's files live outside what a setup may write, and a setup may not put
  symlinks in the sandbox's hook, runtime or config paths.
